# CIndRA Product Assembly — Combined Phase A-F Skill

## Purpose

Use this skill for downstream CIndRA product-package assembly and review preparation. It combines Phases A-F into one coherent workflow because the phases are tightly coupled and usually needed together when preparing products for scientific review or report development.

This skill assembles and audits products that already exist or are generated by approved CIndRA workflows. It does **not** create new scientific methods, revise QC thresholds, introduce alternate data sources, or add ad hoc plots outside approved sea-level workflows and plotting-helper policy.

## Triggers

Use this skill when the user asks to:

- build or audit a product-profile matrix;
- create or update a product inventory;
- write or check captions;
- prepare methods notes or limitations notes;
- create metadata, provenance, source/version, parameter, method-version, or run records;
- validate package completeness;
- assign or audit validation/review status;
- maintain an issue log;
- assemble a structured product section;
- prepare a review package;
- create a DOCX/PDF/Markdown report section;
- prepare code repository materials, annotated notebooks, or product-to-code crosswalks, when explicitly requested.

## Required Inputs

Use outputs from upstream CIndRA skills and repository workflows:

- active product profile: `Regional` or `National/EEZ`;
- site configuration and spatial/station inventory;
- QC status and QC reference for station products;
- generated figures, maps, plots, tables, and metric files;
- method IDs and source-version records;
- repository/notebook/function/helper references;
- available captions, methods notes, limitations notes, provenance, validation records, and issue logs;
- user-requested report/package format.

## Core Guardrails

- Assemble only products supported by approved workflows or explicitly labeled exploratory products.
- Do not invent missing values, figures, tables, methods, captions, validation status, or review status.
- Do not hide missing products, failed validation checks, deferred products, or unresolved issues.
- Do not change methods, QC rules, source hierarchy, product-profile requirements, review-status rules, or figure-helper policy.
- Do not use report files as the source of record; machine-readable CSV/JSON/YAML backbone files remain authoritative.
- Do not mark products `Approved for report use` without human scientific review and complete validation/provenance records.

## Phase A — Product Profile Matrix and Product Inventory

### Purpose

Create or audit the inventory that defines required, optional, supporting, diagnostic, deferred, and missing products for a CIndRA sea-level package.

### Inventory Fields

Track, where applicable:

- `product_id`
- `product_family`
- `product_role`: required primary, supporting, diagnostic, optional, deferred, or missing
- `product_profile`: `Regional` or `National/EEZ`
- `spatial_scope`
- `station_or_source_ids`
- `output_path`
- `output_type`: figure, map, plot, table, metric, text, report, metadata
- `source_data`
- `method_id`
- `qc_reference`
- `caption_status`
- `methods_note_status`
- `provenance_status`
- `validation_status`
- `review_status`
- `issue_log_reference`

### Phase A Rules

- Required products must be included or explicitly deferred with rationale.
- Optional/supporting/diagnostic products must be labeled.
- Missing products must not be hidden.
- Product profiles control scope and layout, not scientific method.
- Product IDs should be stable and traceable across captions, provenance, validation, and report assembly.

## Phase B — Captions

### Purpose

Create concise, traceable captions for figures, maps, plots, and tables using approved product outputs and metadata.

### Caption Requirements

Each caption should state:

- product ID or figure/table ID;
- indicator and product profile;
- spatial scope and station/source IDs where relevant;
- analysis period;
- data source/version where concise;
- units and datum/reference;
- method summary or method ID;
- QC status/reference for station products;
- product role/status;
- key limitation needed for interpretation.

### Sea-Level Caption Rules

- Tide-gauge products must be described as **relative sea level**.
- Altimetry products must be described as **absolute sea level**.
- Combined trend maps must state that absolute altimetry and relative tide-gauge quantities are displayed together but not merged.
- Flood products must state `30 cm above MHHW`, daily maxima, and May-April storm-year convention.
- Monthly flood products must state whether values are counts or percent contributions and define the denominator for percentages.

## Phase C — Methods and Limitations Notes

### Methods Notes

Methods notes should identify:

- indicator family;
- product profile;
- analysis period;
- site/station/spatial scope;
- data sources and source hierarchy;
- repository notebook/function references;
- method ID;
- QC reference and datum/threshold requirements;
- units and baseline/tidal epoch;
- spatial extraction or aggregation method;
- approved plotting helper used for generated figures.

### Limitations Notes

Limitations should address:

- data completeness and QC flags;
- datum availability and compatibility;
- station/grid mismatch;
- absolute-versus-relative sea-level distinction;
- boundary fallback or bounding-box-only limitations;
- provisional trend endpoints;
- optional/exploratory product status;
- unresolved validation issues;
- review status.

## Phase D — Metadata and Provenance

### Purpose

Maintain machine-readable metadata and provenance records. These are the source of record; report files are assemblies only.

### Required Backbone Records

Preserve or reference, where applicable:

- `station_inventory.csv`
- `spatial_selection.json`
- `data_coverage.csv`
- `station_trend_summary.csv`
- `altimetry_trend_summary.csv`
- `integrated_trend_comparison.csv`
- `national_eez_combined_trend_summary.csv`
- `regional_trend_summary.csv`
- `flood_frequency_summary.csv`
- `product_inventory.csv`
- `provenance.json`
- `parameters.json`
- `method_versions.json`
- `source_versions.json`
- `validation_checklist.csv` or `.json`
- `issue_log.csv`
- workflow/run record.

### Required Provenance Fields

For each output or narrative claim, track dataset name, provider, URL/path, version, access date, DOI/citation, station/source ID, variable names, temporal resolution, units, datum/reference, spatial extraction method, source priority, source status, method ID, QC reference, product profile, analysis period, output path, and review status.

### Code Reference Policy

By default, preserve repository URL/path, notebook/function references, method IDs, workflow version, run timestamp, and environment summary where available. Do not furnish a full `Code repository/` bundle unless explicitly requested or contractually required. If not furnished, record status as `not_furnished_unless_requested`.

## Phase E — Validation, Review Status, and Issue Log

### Status Labels

Use only:

- `Experimental`
- `Draft`
- `Scientist-reviewed`
- `Approved for report use`
- `Deferred`
- `Optional`

Do not label products `Approved for report use` without human scientific review and complete validation/provenance records.

### Validation Checklist

Confirm:

- request is within sea-level MVP scope or labeled exploratory;
- active `product_profile` is `Regional` or `National/EEZ`;
- site configuration and station identity are documented;
- QC skill was applied to station products;
- station-level Level 2 screening is used as a station/timeframe gate;
- true no-data periods remain missing/empty/`NaN`;
- relative tide-gauge and absolute altimetry products remain distinct;
- trend products use `1993-2025` unless provisional/diagnostic;
- trend rates use `mm/yr`; epoch changes use `cm` or `cm/epoch`;
- flood products use daily maxima and `30 cm above MHHW`;
- monthly flood products distinguish counts from percentages;
- data-source hierarchy and UHSLC version rules are followed;
- figures use approved plotting helpers;
- required provenance and product inventory records exist;
- report outputs are labeled as review assemblies.

### Issue Log Fields

Track issue ID, product ID, severity, status, description, blocking status, recommended action, responsible reviewer if known, date opened, date resolved, and affected outputs.

### Code Bundle Status

Because code repositories are furnished only upon request, absence of `Code repository/`, annotated notebook, or crosswalk is not a validation failure unless explicitly requested or contractually required. If not requested, record `not_furnished_unless_requested`. If requested but not produced, record `missing`, `deferred`, or `not_applicable` with rationale.

## Phase F — Structured Product Section and Report Assembly

### Purpose

Assemble a review-ready structured product section from generated products and Phase A-E backbone materials. This is not a full interpretive report narrative and must not generate broad decision-support recommendations unless separately approved.

### Recommended Section Structure

Use this order unless the user or design contract specifies otherwise:

1. Package heading: indicator, product profile, spatial scope, package ID, generated date, review status.
2. Product-profile summary: required products, optional/supporting/diagnostic products, deferred/missing products.
3. Primary products: maps, plots, tables, captions, source, method ID, validation status, review status.
4. Supporting or diagnostic products.
5. Methods summary.
6. Limitations summary.
7. Metadata and provenance summary.
8. Validation and review status.
9. Repository and reproducibility reference.
10. Code repository section only if explicitly requested or required.
11. Draft report outputs if report assembly is requested.
12. Appendix or linked backbone files.

### Product-Level Assembly Template

For each product, include:

- Product ID
- Product role
- Output path
- Caption
- Source
- Method ID
- Period/spatial scope
- Validation status
- Review status
- Notes/caveats
- Code reference if furnished or requested
- Report reference if applicable

### Report Outputs

When report assembly is requested, preferred outputs are:

- `report_section/structured_product_section.md`
- `report_section/structured_product_section.docx` where editable review output is needed
- `report_section/structured_product_section.pdf` for fixed-layout review
- `report_section/structured_product_section_metadata.json`
- `report_section/product_report_draft.md`, `.docx`, and/or `.pdf` when a draft report is requested.

Draft reports should include heading/status/profile/scope metadata, product-inventory figures/tables/maps, captions, concise methods summary, limitations notes, provenance summary, validation status, issue-log summary, and clear labels for deferred/optional/diagnostic/missing products.

Report PDFs, DOCX files, and Markdown files are review assemblies. They do not replace machine-readable backbone files.

## Code Repository Furnishing Policy

The `Code repository/` subdirectory, annotated Jupyter notebook, and product-to-code crosswalk are **not furnished automatically**. They are prepared only when:

- the user explicitly requests a code repository, annotated notebook, product-to-code crosswalk, reproducibility bundle, or notebooks;
- a project delivery agreement explicitly requires them;
- a reviewer requests them during scientific or technical review.

When not requested, include a concise repository/reproducibility reference in the structured product section and record code bundle status as `not_furnished_unless_requested`.

When requested, create a package subdirectory named exactly `Code repository/` and include, where applicable:

| Item | Expected content |
|---|---|
| `Code repository/README.md` | Code bundle purpose, repository source, run status, and relationship to generated products. |
| `Code repository/annotated_product_generation.ipynb` | Annotated notebook showing the approved code path used for included products. |
| `Code repository/product_code_crosswalk.csv` or `.json` | Product ID, output filename, notebook section/cell, source helper/function, method ID, and source data. |
| `Code repository/environment_summary.txt` or `.yml` | Software environment and key package versions. |
| `Code repository/code_version.txt` | Repository URL/path, commit/version, workflow version, and generation timestamp. |

The annotated notebook must call approved repository functions/helpers where required, preserve scientific distinctions and QC labels, avoid secrets/private paths, and avoid introducing unapproved methods or visualizations.

If a requested code bundle cannot be produced, record an issue-log entry and label the status `missing`, `deferred`, or `not_applicable`.

## Final Quality Checks

Before finalizing a product package or report section, confirm:

- selected profile, spatial scope, package ID, generated date, and review status are identified;
- all required primary products are included or explicitly deferred;
- optional, supporting, diagnostic, deferred, and missing products are clearly labeled;
- every displayed figure/table/map has a caption;
- methods and limitations are included;
- metadata/provenance summaries and backbone files are referenced;
- validation summary, review status, unresolved issues, and issue-log references are included;
- repository/code reference is included;
- if code bundle was requested, `Code repository/` contents and crosswalk exist or their absence is logged;
- if code bundle was not requested, status is `not_furnished_unless_requested`;
- draft report outputs are labeled as review assemblies, not final approved reports or source-of-record files;
- no broad unsupported narrative, recommendations, or unapproved scientific products were added.
